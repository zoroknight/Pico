# Month 06.1: Camera, Lighting, Spring Arm, and Named Sockets

## Goal

Introduce a small runtime camera and lighting layer without coupling engine objects to OpenGL or
editor UI. The implementation follows the UE separation between the editor viewport camera,
runtime camera components, light components, and `USpringArmComponent`.

## Runtime Components

- `PCameraComponent` owns active state, vertical field of view, and near/far clip planes.
- `PLightComponent` owns enabled state, linear RGB color, and intensity.
- `PDirectionalLightComponent` derives its direction from its world rotation.
- `PPointLightComponent` owns an attenuation radius and derives its position from its world transform.
- `PSpringArmComponent` owns target length, socket offset, and world-space target offset.

All editable fields are reflected. They therefore use the existing generic Details panel,
property transactions, world serialization, `PostLoad`, and `PostEditChangeProperty` validation.

## Named Socket Model

An attachment now consists of:

```text
Child RelativeTransform
Child AttachParent
Child AttachSocketName
```

`PSceneComponent::DoesSocketExist` validates a requested name and
`PSceneComponent::GetSocketTransform` resolves its world transform. A normal scene component only
supports the unnamed origin. Spring Arm additionally supports `SpringEndpoint`.

This is deliberately general enough for a future skeletal mesh implementation. A skeletal mesh
component can expose bone and authored socket names through the same two virtual functions; child
components do not need to know whether their parent socket came from a spring arm, a static socket,
or an evaluated skeleton pose.

World format v3 stores the socket name in each attachment relation. The loader still accepts v1
and v2 scenes, which restore attachments to the unnamed component origin.

## Rendering

`TryBuildActiveCameraView` traverses runtime scene components and builds an `FSceneView` from the
first active Camera. `GatherSceneLighting` extracts the first enabled Directional Light and up to
four enabled Point Lights.

The OpenGL PBR shader now evaluates each extracted light. A scene with no authored lights keeps the
previous default directional light for compatibility. Once any Light component is authored,
including a disabled one, lighting is controlled entirely by the scene.

## Editor Workflow

The `Add` and `Add Component` menus expose Camera, Spring Arm, Directional Light, and Point Light.
Creation uses `FEditorCommandService`, so Undo/Redo and selection restoration work without UI-only
object mutations.

Adding a Camera while a Spring Arm is selected automatically attaches it to `SpringEndpoint`.
The toolbar `Scene Camera` checkbox previews the first active runtime Camera. The editor fly camera
remains separate and right-mouse navigation is suspended during scene-camera preview.

Non-renderable components use editor-only wireframe visualization generated by `PicoRender`:

- Camera components draw a blue field-of-view frustum.
- Directional Lights draw a yellow direction arrow.
- Point Lights draw a compact orange icon; the real three-axis attenuation sphere appears only
  while the Point Light Actor or Component is selected.
- Spring Arms draw a purple line from their origin to `SpringEndpoint`.

The wireframes participate in viewport picking and turn white when their Component or owning Actor
is selected. They are transient draw data: they do not create meshes, assets, runtime objects, or
serialized scene properties. The active Camera hides its own frustum while it supplies the viewport
view, preventing the frustum from covering the preview.

## Current Boundary

The current Spring Arm implements deterministic geometric offset only. Collision probing, camera
location lag, rotation lag, control rotation inheritance, and physics timestep clamping are deferred.
Those features depend on later physics queries, richer tick configuration, and controller/view-target
concepts; adding them now would create engine-specific shortcuts that would later be replaced.

## Manual Acceptance

1. Add a Cube and a Directional Light. Rotate the light and edit its color/intensity; the cube shading changes.
2. Add a Point Light. Move it around the cube and change `AttenuationRadius`; illumination follows its position.
3. Add a Spring Arm Actor, select its root component, and add a Camera Component.
4. Change `TargetArmLength`, `SocketOffset`, and `TargetOffset`; the Camera world transform follows the endpoint.
5. Enable `Scene Camera`; the viewport switches from the editor camera to the runtime Camera.
6. Save and reopen the world; the Camera remains attached to `SpringEndpoint` and the light settings persist.
7. Undo and redo Camera/Light creation and property edits.
8. Confirm each non-renderable component has a wireframe, follows gizmo transforms immediately,
   can be clicked in the viewport, and turns white when selected.

Automated coverage verifies component registration, endpoint transforms, socket serialization and
reconstruction, transactional editor creation, active-camera extraction, and scene-light gathering.
